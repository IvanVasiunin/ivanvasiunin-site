> **Overrides (decided 2026-11-01). These take precedence over the text below:**
> - CSS units: `rem` for font-size / typography, `px` for borders (not `px` everywhere as in 4.2).

## 0. Как работать

- Общайся со мной **на русском**. Все файлы в репозитории (CLAUDE.md, SPEC.md, rules, ADR, комментарии в коде) пиши **на английском**: репозиторий публичный и входит в портфолио.
- Не полагайся на память в вопросах версий, API и названий пакетов. Проверяй по официальной документации: через Context7 MCP, когда он будет подключён, или через веб-поиск. Если что-то проверить не удалось, пометь это как `UNVERIFIED`.
- Не выдумывай пакеты, MCP-серверы и плагины. Для каждого укажи официальный источник, лицензию, дату последнего релиза и зачем он нужен именно в этом проекте.
- По возможностям Claude Code (CLAUDE.md, `.claude/rules/`, skills, subagents, hooks, settings, output styles, MCP, plugins) сверяйся с официальной документацией: https://code.claude.com/docs. Можно через встроенного агента `claude-code-guide`.
- **Принцип «правило → инструмент».** Всё, что можно проверить линтером, форматтером, тайпчекером или hook'ом, проверяется автоматически. В CLAUDE.md и rules остаётся только то, что автоматизировать нельзя.
- **Принцип «у каждой технологии есть роль».** AI-стек используется широко, потому что сайт — витрина навыков AI Engineer. Но для каждого компонента должна быть записанная причина в виде ADR. Ответ на вопрос «зачем здесь LangGraph?» должен лежать в репозитории.
- Если что-то в этом документе устарело или противоречит хорошим практикам, скажи прямо и предложи замену. Не выполняй слепо.
- Перед действиями с побочными эффектами вне репозитория всегда спрашивай. Это глобальные установки, изменение моих user-настроек Claude Code и `git push`.
- После каждого этапа присылай короткий отчёт: что сделано, что решено, что требует моего решения.

## 1. Контекст проекта

### 1.1 Цель
Личный сайт-визитка Ивана. Сейчас я Senior Markup Developer и перехожу в AI Engineering. Сайт должен:
- рассказывать обо мне и моём опыте;
- демонстрировать навыки:
  - AI-инженерию: RAG, LangChain/LangGraph, LLM API, эмбеддинги и их визуализацию, evals, guardrails;
  - качественную вёрстку;
- сам быть портфолио-проектом с публичным кодом и архитектурой на GitHub.

Это **мой первый AI-проект**. Поэтому важно не только чтобы всё работало, но и чтобы я понимал каждое решение в AI-части и мог объяснить его на собеседовании (см. 1.8).

### 1.2 Структура сайта
Два режима, переключаемых верхними табами. У каждого режима свой URL.

**AI mode:**
- **Чат** с AI-ассистентом обо мне в стиле Claude или ChatGPT, со стримингом ответа.
- **Живое векторное пространство** на фоне — 2D-карта всех кусков базы знаний обо мне.
  - Точки медленно дрейфуют.
  - Когда ассистент находит источники для ответа, соответствующие точки плавно подсвечиваются: чем релевантнее, тем ярче.
  - Рендер на SVG (см. 4.5).
- **Панель Under the hood** под каждым ответом, раскрывается по клику. Показывает:
  - что решил роутер;
  - найденные источники с релевантностью и коротким фрагментом;
  - время по шагам графа;
  - токены и примерную стоимость.

  Системный промпт и внутреннюю конфигурацию панель не показывает никогда.

**Text mode** — CV:
- Лёгкая быстрая страница. Всё основное работает без JS.
- **Переключатель Brief / Full**: короткая выжимка для рекрутера и полная версия.
- **Кнопки «Ask about this»** у мест работы и групп навыков. Кнопка открывает AI mode с готовым вопросом в поле ввода. Вопрос **не отправляется автоматически**, чтобы случайный клик или поисковый бот не тратил деньги на LLM.
- **Детали вёрстки** (оба пункта — как progressive enhancement):
  - scroll-driven анимации на чистом CSS;
  - View Transitions при переключении режимов.
- Печатная версия и PDF.
- **CV хранится в одном структурированном источнике.** Из него собираются HTML-страница, PDF и данные для RAG, поэтому версии не расходятся. Есть готовое CV в Word: `data/raw/CV_Ivan_Vasiunin.docx` (папка `data/raw/` в `.gitignore`, потому что там мой телефон). В фазе Text mode Claude собирает структурированный исходник из этого CV и `data/experience-notes.md`, а я ревьюю. Номер телефона не попадает ни в исходник CV, ни в RAG, ни на сайт. После этого experience-notes остаётся источником подробностей, а не второй копией CV.

**Мобильная версия обязательна** для обоих режимов:
- ширина от 360px;
- портретная и альбомная ориентация;
- тач-управление.

Сайт обязан нормально работать на слабых устройствах. Подробные требования — в разделе 4.12.

### 1.3 AI-ассистент

**Источники для RAG:**
- CV — единый источник из 1.2;
- LinkedIn-экспорт в RAG **не загружается**: рекомендаций в нём нет, а всё полезное уже перенесено в `experience-notes.md`. Дубли ухудшили бы retrieval;
- `data/about-me-personal.md` — личная информация для тех, кто хочет узнать меня как человека;
- `data/experience-notes.md` — заметки об опыте по каждому месту работы в формулировках, безопасных для NDA;
- **документация самого сайта**: SPEC.md, ADR, ARCHITECTURE.md. Так ассистент сможет рассказать, как устроен этот сайт и почему решения приняты именно так;
- README из GitHub-репозиториев по allowlist (список — в 1.9). Сейчас это в основном учебные проекты, они явно помечаются как учебные. Эти проекты уже кратко описаны в `experience-notes.md`, поэтому ingestion помечает README как `type=github_readme`, а retrieval не должен возвращать подряд несколько почти одинаковых фрагментов про один проект (дедупликация по проекту);
- дополнительные материалы, которые я добавлю.

**NDA.** Мои рабочие проекты, скорее всего, под NDA.
- В данные и ответы попадают только роль, тип продукта, стек и мой вклад общими словами.
- На вопросы о внутренних деталях ассистент отвечает, что это под NDA, а в общих чертах Иван может рассказать на собеседовании.

**Стек:**
- Векторная БД обязательна.
- LLM по API: дешёвая модель для роутинга, сильная для ответа.
- **Провайдер на старте — OpenAI** (у меня на балансе около $20). Позже, возможно, переключусь на Claude (Anthropic). Требования:
  - провайдер и model ID выбираются в конфиге, без правок кода (например, через `init_chat_model` из LangChain); переключение покрыто тестом;
  - эмбеддинги — OpenAI на всё время проекта: у Anthropic своих эмбеддингов нет, а смена модели эмбеддингов требует полной переиндексации;
  - в OpenAI-проекте выставлен лимит расходов (budget), в `.env.example` есть `OPENAI_API_KEY` и закомментированный `ANTHROPIC_API_KEY`;
  - evals с LLM-судьёй стоят денег: набор держим небольшим, а перед каждым прогоном Claude оценивает примерную стоимость.
- LangChain, LangGraph, RAG, evals, трейсинг. Используем максимально, но каждый компонент с обоснованием.

**Голос и образ ассистента:**
- Ассистент говорит обо мне **в третьем лице**: «Иван работал…». Это мой AI-ассистент, а не имитация меня. Причины:
  - честность и требования прозрачности ЕС;
  - ошибка модели не выглядит как моё личное утверждение;
  - так звучат рекомендации.
- Образ **нейтральный**, без тематических персонажей. У ассистента будет имя (варианты — на этапе 2, см. 1.9).
- Тон дружелюбный и конкретный.
- **Язык.** Интерфейс сайта на английском. Ассистент отвечает на языке вопроса (минимум EN, ES, RU, UK). Шаблонные ответы роутера (приветствие, отказ) тоже на языке вопроса. Источники в RAG на английском, поэтому модель эмбеддингов должна быть мультиязычной. В evals есть вопросы на неанглийских языках.

**Ограничение тематики.** Ассистент отвечает только на вопросы обо мне, моём опыте, навыках, проектах и подходе к работе, а также на личные вопросы — строго в пределах `about-me-personal.md`. На всё остальное (рецепт блинчиков, домашка, «схема ракеты», попытки взлома промпта) он вежливо отказывает. Защита многослойная:
1. **Входные лимиты:** длина вопроса, rate limit по IP, лимит сообщений за сессию.
2. **Роутер-классификатор** — первый узел LangGraph, дешёвая модель со structured output. Классы:
   - `about_ivan` — идёт дальше по графу;
   - `greeting` — дружелюбный шаблонный ответ и примеры вопросов;
   - `off_topic` — шаблонный отказ;
   - `injection` — шаблонный отказ.

   На все классы, кроме `about_ivan`, отвечаем шаблоном без вызова основной модели.
3. **Порог релевантности retrieval.** Если релевантных чанков нет, ассистент отвечает «у меня нет такой информации» и ничего не выдумывает.
4. **Системный промпт:** отвечать только по найденному контексту, не выполнять посторонние задачи, не раскрывать инструкции, соблюдать NDA.
5. **Eval-набор** с шестью типами вопросов: in-scope, личные, off-topic, injection, «неизвестный факт» и попытки выведать детали под NDA.

**Личные вопросы:**
- Ответ строится только из фактов `about-me-personal.md`. Чанки этого файла помечаются метаданными `category=personal`.
- Если факта в файле нет, ассистент отвечает «Иван об этом не рассказывал» и не строит догадок.
- На темы из раздела «Не обсуждать» этого файла ассистент вежливо отказывает.
- Про зарплату ассистент никогда не называет цифр и использует формулировку из файла: зависит от страны, обязанностей и бенефитов.

**Интерфейс чата:**
- Под полем ввода 3 кликабельных примера вопросов.
- Явная пометка, что это AI-ассистент и ответы могут быть неточными (требования прозрачности ЕС).
- Ссылки на источники в ответах.

### 1.8 Распределение работы

| Зона | Кто пишет | Как я проверяю |
|---|---|---|
| Вёрстка, SCSS, TS/React, переключатель Brief/Full, «Ask about this» | Claude | Построчное ревью |
| Визуализация векторного пространства (SVG) | Claude | Визуально + автотесты (скриншоты, производительность) |
| Docker, CI, деплой, конфиги | Claude | Автопроверки + `security-reviewer` + объяснение каждого файла |
| **AI-ядро:** ingestion, чанкинг, эмбеддинги, 2D-проекция, векторное хранилище, retrieval, роутер, граф LangGraph, промпты, evals | **Я + Claude — наставник, с пошаговыми подсказками и рекомендациями** | Claude ревьюит мой код |

**Правила для зон, где пишет Claude:**
- Работа идёт маленькими шагами. Один шаг — одно логичное изменение, которое я реально отревьюю за 10–15 минут. Ориентир — до ~300 строк диффа.
- К каждому шагу прилагается:
  - что сделано и почему;
  - какие альтернативы отброшены;
  - чек-лист «что проверить» для меня;
  - результаты проверок.
- К следующему шагу Claude переходит только после моего OK.

**Режим наставника (зона AI-ядра):**
- Claude **не пишет реализацию** в зоне AI-ядра, пока я явно не попрошу («напиши это за меня»).
- Формат задачи:
  1. цель;
  2. контекст: какие библиотеки, ссылки на документацию;
  3. Claude заранее пишет падающие тесты;
  4. Claude говорит, что нужно реализовать следующим шагом и я пишу код;
  5. Claude ревьюит как наставник: объясняет, что и почему можно улучшить, но не переписывает за меня, только по моему запросу.
- Подсказки выдаются по уровням: сначала наводящий вопрос, потом направление, потом пример на похожем, но другом коде. Готовое решение — только по просьбе.
- После каждой задачи Claude задаёт 2–3 вопроса «explain-back», и я своими словами объясняю, что и зачем сделано.
- Если я скажу, что так слишком медленно, переходим на компромисс: реализацию пишет Claude, а я пишу тесты и отвечаю на explain-back вопросы.
- Проверь, есть ли в Claude Code подходящий встроенный режим вывода (output style) для обучения, и предложи использовать его в этой зоне.
- **Тесты моих незавершённых задач** помечаются специальным маркером, например pytest-маркером `mentor_pending`. Они исключены из быстрых проверок и Stop hook, пока я не скажу, что задача готова. Stop hook никогда не должен подталкивать Claude дописать код в зоне наставника. Это единственное разрешённое исключение из правила «красный тест нельзя пропускать».

### 1.9 Принятые решения
- **CSS-нейминг:** BEM.
- **Язык:** интерфейс на английском, ассистент отвечает на языке вопроса (см. 1.3).
- **Имя ассистента:** нужно. На этапе 2 предложи 5 нейтральных вариантов: короткие, легко произносимые, без отсылок к реальным продуктам и брендам.
- **Режим по умолчанию — AI mode.** Значит:
  - «/» — это AI mode, но с серверно отрендеренным HTML: кто такой Иван (1–2 предложения), примеры вопросов и ссылка на CV. Это нужно для SEO, предпросмотров ссылок и для пользователей без JS;
  - CV живёт на отдельном URL (например, `/cv`);
  - бюджеты производительности AI mode становятся бюджетами главной страницы.
- **Дизайна нет**, делаем по ходу. Нужны светлая и тёмная темы: по умолчанию по `prefers-color-scheme`, плюс ручной переключатель, выбор запоминается.
- **Allowlist GitHub для RAG:** NumbersValidator, smart-test-task, blaize-test-task, Coursera-capstone-project, nextjs-app, events-app-with-tanstack-query, shop-with-react-redux, food-order-app.v2.0, placepicker_v2.0, react-project-managment-app, а после публикации — репозиторий этого сайта.
- **Эмбеддинги:** OpenAI. Конкретную модель выбери на этапе 2 по актуальной документации: дешёвая и мультиязычная.
- **Аналитика:** на старте не нужна. Вместо неё — анонимная статистика чата: сколько вопросов, классы роутера, доля ответов «нет информации», ошибки. Тексты вопросов храним только обезличенными и с ограниченным сроком (см. privacy). Self-hosted Umami — в backlog.
- **Домен:** планируется `ivanvasiunin.com`, пока не куплен. VPS тоже пока нет.
- **Репозиторий:** публичный на GitHub.
- **Наставничество:** Claude пишет падающие тесты, я пишу реализацию (см. 1.8).
- **Исходник CV:** предложи формат на этапе 2. Моя гипотеза: одна Markdown-запись на каждое место работы и раздел CV, с YAML frontmatter (компания, должность, даты, стек, `brief` — короткая версия), а тело файла — полная версия. Схема валидируется при сборке (например, Astro content collections + Zod).

## 4. Требования по технологиям (seed — расширь)

Каждый блок ниже станет отдельным файлом в `.claude/rules/` с frontmatter `paths:`, чтобы правило загружалось только при работе с соответствующими файлами.

Как расширять:
- только конкретные, проверяемые правила, без общих слов вроде «пиши чистый код»;
- у каждого правила метка способа проверки: `[lint]`, `[hook]`, `[test]`, `[settings]` или `[review]` (только ревью).

### 4.1 HTML, семантика, доступность
- Семантические теги: `header`, `nav`, `main`, `section`, `article`, `footer`. Один `h1` на страницу, уровни заголовков без пропусков.
- Навигация — `<a>`, действия — `<button>`. Кликабельные `div` и `span` запрещены. `[lint]`
- Табы режимов — по паттерну WAI-ARIA Tabs: `role="tablist"/"tab"/"tabpanel"`, `aria-selected`, управление стрелками. У каждого режима свой URL, которым можно поделиться.
- Переключатель Brief/Full — кнопки с `aria-pressed`. Выбор сохраняется в URL (например, `?view=brief`).
- `img`: всегда `alt` (декоративные — `alt=""`) и `width`/`height` против CLS. `[lint]`
- Поле чата: связанный `label` или `aria-label`.
- Стриминг ответа не зачитывается по токенам. Ответ анонсируется через `aria-live="polite"` по завершении.
- Under the hood — раскрывающаяся панель с `aria-expanded`, управляется с клавиатуры.
- `lang` на `<html>`, meta/OG-теги, JSON-LD `Person` на CV.
- Контраст — WCAG 2.2 AA. `[test]`

### 4.2 CSS / SCSS
- Раскладка только Grid/Flex. `float` запрещён. `[lint]`
- `!important` запрещён. `[lint]`
- `position: absolute/fixed` — только для оверлеев и декора, не для раскладки. `[review]`
- У каждого интерактивного элемента есть состояния:
  - default;
  - `:hover` — только внутри `@media (hover: hover)`, чтобы на тач-устройствах не залипал;
  - `:focus-visible`;
  - `:active`;
  - `:disabled` / `[aria-disabled="true"]`;
  - loading — для асинхронных действий.

  `outline: none` без замены запрещён. `[review]`
- Любое изменение состояния анимируется через `transition` с токенами длительности и easing. `transition: all` запрещён — свойства перечисляются явно. `[lint]`
- Анимируются только `transform` и `opacity`. `width`, `height`, `top`, `left`, `margin` не анимируются. `[review]`
- При `prefers-reduced-motion: reduce` анимации отключаются или сокращаются. `[review]`
- Scroll-driven анимации и View Transitions подключаются только внутри `@supports` / проверки поддержки. Без них страница полностью работает. `[review]`
- Дизайн-токены — CSS custom properties: цвета, отступы, типографика, радиусы, тени, длительности, easing, z-index (только из шкалы). Без магических чисел. SCSS-переменные и миксины — только для build-time вещей вроде брейкпоинтов. `[lint, где возможно]`
- Mobile-first. Брейкпоинты через миксины, container queries для компонентов, где уместно.
- Единицы: `px` для типографики и отступов, `clamp()` для fluid-типографики. `[lint]`
- Логические свойства: `margin-inline`, `padding-block` и т.п.
- Низкая специфичность:
  - без ID-селекторов `[lint]`;
  - вложенность SCSS не больше 3 `[lint]`;
  - `:where()` в ресетах;
  - cascade layers `@layer reset, base, components, utilities`.
- Градиентные рамки делаются через `border: 1px solid transparent` + `background-image` + `background-clip` / `background-origin`, а не через `mask` — из-за производительности. `[review]`
- Есть печатные стили: при печати CV всегда показывается полная версия, без навигации и фонов. `[test]`
- Нейминг — BEM, единообразно во всём проекте. `[lint]`

### 4.3 TypeScript
- `strict: true` и `noUncheckedIndexedAccess`. `[lint]`
- `any` запрещён: используй `unknown` и сужение типа. `[lint]`
- Non-null assertion `!` — только с комментарием-обоснованием. `[lint]`
- Типы контракта API (включая события SSE) берутся из одного источника: генерация из OpenAPI-схемы FastAPI или общий пакет типов. Предложи решение.
- Named exports. Default export — только там, где его требует фреймворк. `[lint]`

### 4.4 React
- Только функциональные компоненты и хуки.
- Компонент — это папка: `Component.tsx`, стили, тест, пропсы через `interface`.
- Состояние локальное. Глобальный стор — только при доказанной необходимости.
- У эффектов есть очистка. Стриминг чата отменяется через `AbortController` (кнопка Stop).
- Inline-стили запрещены, кроме передачи динамических значений через CSS-переменные. `[lint]`
- Error boundary вокруг чата и визуализации.
- Ответы модели рендерятся как Markdown без сырого HTML, с санитизацией. `[test]`
- «Ask about this» только заполняет поле ввода и ставит на него фокус. Запрос не отправляется без действия пользователя. `[test]`
- Переключатель Brief/Full: без JS показывается полная версия. `[test]`

### 4.5 Визуализация векторного пространства (SVG)
- **Данные:**
  - статичный JSON точек: id чанка, x, y, тип источника, раздел. Генерируется на этапе ingestion, текстов чанков в нём нет;
  - бюджет — не больше 200 KB gzip;
  - id точек совпадают с id чанков, которые API возвращает в событии `sources`. `[test]`
- **Разметка:** SVG с `viewBox`, масштабируется под контейнер, плотность и размер точек адаптированы для мобильных.
- **Доступность:** визуализация декоративная (`aria-hidden="true"`). Информация о найденных источниках всегда дублируется текстом в Under the hood. `[review]`
- **Анимации:**
  - только `transform` и `opacity` через CSS;
  - без SMIL;
  - без покадрового изменения атрибутов из JS. `[review]`
- **Свечение:** никаких SVG-фильтров (`feGaussianBlur` и т.п.) на сотнях анимируемых элементов. Используй общий `radialGradient` в `<defs>` или заранее подготовленные формы. `[review]`
- **Масштаб:** ориентир — до ~1000 DOM-узлов точек. Если больше, нужен ADR о переходе на Canvas 2D.
- **Пауза:** дрейф останавливается, когда визуализация вне экрана (IntersectionObserver) или вкладка скрыта. При `prefers-reduced-motion` дрейфа нет, подсветка остаётся без движения.
- **Подсветка:** класс или атрибут на точках по списку id, интенсивность по релевантности, плавные transitions. Легенда поясняет, что означают точки.
- **Цвета** точек по типу источника (CV, опыт, личное, документация сайта, GitHub) берутся из токенов. Подсветка достаточно контрастна в обеих темах.
- **Тесты:** логика (масштабирование координат, выбор подсвечиваемых точек, интенсивность) покрыта unit-тестами. `[test]`
- **Визуальная планка (decision gate):**
  1. сначала прототип на моковых данных;
  2. скриншоты desktop и mobile в светлой и тёмной теме;
  3. замер производительности с CPU throttling 4× и 6×;
  4. я решаю, достаточно ли это красиво.

  Если нет — ADR с вариантами (Canvas 2D, WebGL), их стоимостью и тем, как я смогу проверять такой код.

### 4.6 Контент, NDA и лицензии
- В контенте, данных для RAG, скриншотах и ответах ассистента нет конфиденциальных деталей работодателей: внутренних названий систем, кода, непубличных метрик, данных клиентов.
- Логотипы и названия работодателей — только если это разрешено. Сомнение решается в пользу «не использовать».
- Учебные проекты явно помечаются как учебные.
- Шрифты, иконки и прочие ресурсы — только с открытыми лицензиями (OFL, MIT, ISC и т.п.). Каждый записан в `docs/CREDITS.md`. Шрифты на самохостинге.

### 4.7 Python
- Версия закреплена в `.python-version`. Зависимости ставятся через uv. `pyproject.toml` — единственный источник конфигурации.
- Аннотации типов везде. mypy или pyright в strict-режиме или близком к нему. `[lint]`
- ruff для линтинга и форматирования. `[lint][hook]`
- Читаемость важнее краткости:
  - явное лучше хитрого;
  - docstring с объяснением «зачем»;
  - комментарии к неочевидным вызовам библиотек;
  - без «магии».
- В зоне AI-ядра действует режим наставника (1.8): Claude не пишет реализацию без моей просьбы. `[review]`
- Конфигурация — только через pydantic-settings из env. Секретов в коде нет. `[hook]`

### 4.8 FastAPI
- Эндпоинты асинхронные. Внутри async нет блокирующих вызовов: HTTP через async httpx, БД через async-драйвер.
- Все входы и выходы — Pydantic-модели.
- Единый формат ошибок. Стектрейсы клиенту не отдаются.
- **SSE-контракт чата.** Типизированные события, схемы описаны в SPEC.md:
  - `route` — класс роутера;
  - `sources` — id чанков, релевантность, метаданные, короткий фрагмент;
  - `token` — очередной кусок ответа;
  - `usage` — время по узлам, токены, примерная стоимость;
  - `done`;
  - `error`.
- Структура, например: `routers/`, `services/`, `graph/`, `ingestion/`, `evals/`, `core/` (config, logging). Предложи финальный вариант и чётко отметь, какие папки относятся к зоне наставника.
- CORS — только мой домен (и localhost в dev).
- Логирование структурированное. Полные тексты вопросов без необходимости не логируются (privacy).
- Есть healthcheck-эндпоинт.

### 4.9 LangChain / LangGraph / RAG
- Роль каждого компонента записана в ADR:
  - LangChain — загрузчики, сплиттеры, эмбеддинги, интеграция с векторным хранилищем;
  - LangGraph — граф: input guard → router → retrieval → relevance gate → generation или refusal.
- Состояние графа типизировано, узлы — небольшие функции. Граф экспортируется в Mermaid в `docs/ARCHITECTURE.md`.
- Каждый узел графа замеряет время и токены. Эти данные уходят в событие `usage`. Стоимость считается по ценам моделей из конфига.
- Промпты лежат в отдельных версионируемых файлах, а не строками по коду.
- Model ID, температура и лимиты токенов задаются в конфиге.
- Политика тем (разрешённые, запрещённые, пограничные случаи, NDA, зарплата) описана в SPEC.md. Роутер и системный промпт реализуют именно её.
- **Retrieval:**
  - гибридный (вектор + полнотекст) с фьюжном;
  - у чанков есть метаданные: источник, тип, раздел, дата, URL;
  - стратегия чанкинга задокументирована;
  - ответы ссылаются на источники.
- Ниже порога релевантности ассистент отвечает «нет информации» и не берёт знания обо мне «из головы» модели.
- **2D-проекция:**
  - координаты считаются при ingestion детерминированно (фиксированный `random_state`), хранятся вместе с чанками и экспортируются в JSON для фронтенда;
  - как сохранять раскладку стабильной при добавлении данных — описать в ADR.
- Ingestion идемпотентный: повторный запуск не дублирует данные, используется хэш контента.
- **LinkedIn-экспорт** в проект не копируется и в RAG не загружается (см. 1.3).
- GitHub: только публичные репозитории из allowlist.
- Лимиты (длина вопроса, сообщений за сессию, rate limit по IP, max output tokens) задаются в конфиге. Лимиты расходов выставлены у провайдеров.
- Prompt caching для системного промпта: у OpenAI он автоматический для длинных промптов — значит, неизменяемая часть промпта должна идти первой; у Anthropic — явные cache breakpoints. Реализация должна работать с обоими провайдерами.
- Любое изменение промптов или retrieval сопровождается прогоном evals до мержа.
- Секреты не попадают в трейсы.

### 4.10 PostgreSQL / pgvector
- Схема меняется только через миграции.
- Размерность вектора соответствует модели эмбеддингов. Есть HNSW-индекс и FTS-индекс для гибридного поиска.
- БД недоступна извне, только из внутренней сети docker compose.
- Бэкапы через `pg_dump` по расписанию описаны в RUNBOOK.

### 4.11 Тестирование

**Пирамида тестов:**
- **Unit.**
  - Vitest — логика фронтенда: парсинг SSE, состояние чата, Brief/Full, «Ask about this», логика визуализации.
  - pytest — сервисы, узлы графа, чанкинг, проекция, лимиты.
  - LLM-вызовы замоканы.
- **Компоненты.** Vitest + Testing Library. Проверяются все состояния (default, focus, disabled, loading, error, empty) и управление с клавиатуры.
- **API и контракт.** pytest + httpx AsyncClient: схемы ответов, формат ошибок, rate limit, все типы событий SSE. Типы на фронтенде совпадают с OpenAPI-схемой. `[test]`
- **E2E.** Playwright, на desktop и мобильных профилях:
  - переключение режимов, табы с клавиатуры;
  - Brief/Full и сохранение выбора в URL;
  - «Ask about this» заполняет поле и не отправляет запрос;
  - чат со стримингом на моке LLM, кнопка Stop, сетевые ошибки;
  - содержимое Under the hood;
  - подсветка точек после ответа.
- **Визуальная регрессия.** Playwright-скриншоты ключевых экранов на ширинах 360, 768 и 1440, в светлой и тёмной теме, плюс печатная версия CV.
- **A11y.** axe в e2e на каждом экране. Ноль нарушений уровня serious/critical. `[test]`
- **Производительность.**
  - Lighthouse CI с бюджетами для mobile- и desktop-профилей;
  - замер длинных кадров во время дрейфа и подсветки точек при CPU throttling (см. 4.12).
- **RAG evals.** Отдельная команда, потому что стоят денег. Проверяют:
  - качество ответов: faithfulness, relevance;
  - точность роутера по классам;
  - что «неизвестный факт» даёт ответ «нет информации»;
  - что NDA-вопросы и вопросы о зарплате обрабатываются по политике.

  Пороги задаются в конфиге, падение ниже порога считается провалом.
- **Безопасность.** gitleaks, pnpm audit, pip-audit в CI.

**Правило «после каждой задачи»:**
- Задача не считается выполненной, пока проверки не зелёные.
- После каждого изменения Claude запускает быстрые проверки затронутого приложения: format, lint, typecheck, unit- и компонентные тесты. `[hook]`
- Дополнительно, в зависимости от того, что изменилось:
  - UI или стриминг → e2e затронутых сценариев на desktop и мобильном профиле;
  - визуализация → замер производительности и скриншоты;
  - промпты, retrieval или граф → evals, но только с моего согласия.
- Новая логика сопровождается новыми тестами в том же изменении. Исправленный баг сопровождается тестом, который его воспроизводит.
- В отчёте по каждой задаче есть блок «Проверки»: какие команды запущены и с каким результатом.
- Красный тест нельзя «чинить» ослаблением проверки, `skip` или удалением без моего согласия. Единственное исключение — маркер `mentor_pending` из 1.8.
- Перед коммитом запускается полный набор через skill `pre-pr-check`.
- Покрытие — ориентир, а не самоцель: от 80% строк для `apps/api` (сервисы и граф) и от 70% для фронтенд-логики. Разметку покрытием не меряем.

### 4.12 Мобильная версия и слабые устройства

**Мобильная вёрстка:**
- Mobile-first, минимальная ширина 360px. Проверка на ширинах 360, 390, 768, 1024 и 1440. `[test]`
- Тач-цели не меньше 44×44px. `[review]`
- Никакой функциональности, доступной только по hover.
- `svh`/`dvh` вместо `100vh`. Учитывается safe area (`env(safe-area-inset-*)`) на телефонах с вырезом.
- Чат на мобильном:
  - поле ввода остаётся видимым над виртуальной клавиатурой: meta viewport `interactive-widget=resizes-content` и/или `visualViewport`;
  - сообщения не прячутся под клавиатурой;
  - `font-size` поля не меньше 16px, чтобы iOS не зумил страницу.
- Переключатель режимов удобен одной рукой.
- Визуализация на мобильном не мешает читать чат: она приглушена и не перекрывает текст.

**Слабые устройства:**
- Режим «облегчённой визуализации» включается по сигналам: `navigator.hardwareConcurrency`, `navigator.deviceMemory` (где доступен), `navigator.connection.saveData`, а также при длинных кадрах во время работы. В этом режиме дрейфа нет, остаётся только подсветка.
- **Бюджеты (стартовые, уточнить):**
  - Text mode, mobile-профиль Lighthouse (Slow 4G, CPU throttling): LCP < 2.5 s, CLS < 0.1, INP < 200 ms;
  - Text mode, desktop: LCP < 2.0 s;
  - JS на Text mode — не больше 150 KB gzip;
  - JS на AI mode (чат и визуализация) — не больше 400 KB gzip, JSON точек — не больше 200 KB gzip;
  - время до первого токена ответа на проде (p50) — меньше 2 s;
  - Lighthouse mobile на CV — не ниже 95 по всем четырём категориям.
- **Тесты:**
  - Playwright-проекты с эмуляцией мобильных устройств, сетевым throttling (Slow 4G) и CPU throttling 4× и 6× через Chrome DevTools Protocol;
  - замер доли длинных кадров во время дрейфа и подсветки, сравнение с порогом; `[test]`
  - проверка, что облегчённый режим реально включается. `[test]`
- Профилирование через Chrome DevTools MCP (performance trace) после заметных изменений визуализации.
- Перед релизом — ручная проверка на реальном iPhone 17 Pro Max: Safari, клавиатура в чате, safe area, тёмная тема. Это мощное устройство, поэтому для слабых Android используй эмуляцию с CPU throttling 6×. Предложи бесплатный или пробный облачный сервис реальных устройств, если такой есть. Результаты записываются в `docs/TESTING.md`.
